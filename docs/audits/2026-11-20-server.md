# Server audit, 2026-11-20

Scope: `server/` (routes, services, auth, enrollment, rules, push and mail senders, DNS sync,
rate limits) and `packages/crypto`. The audit looked for authorization and household isolation
holes, input validation, personal data in logs, rate limits, replay, crash paths, slow queries,
unbounded memory, races and untested safety-critical paths.

No P1 finding: no cross-household access, no Self-key bypass, no token or approval replay, and no
way for a child to loosen the rules from the server side was found.

## Fixed on branch `fix/hardening-server`

Each has a test (named below, else in `server/test/hardening.test.ts`) that
fails without the fix.

- **P2: unauthenticated memory exhaustion.** No request body limit, and `RateLimiter` kept every
  key for its whole window (`GET /api/device/pairings/<any string>` added a new key per request).
  Now a 1 MB default body limit on `/api/*` (contact suggestions and server-move import keep their
  own), a key cap in `RateLimiter`, the pairing id checked before the limiter, and the login IP
  limit taken before the body is read.
- **P2: personal data in the server log.** drizzle's `DrizzleQueryError` message holds the
  query's parameters (emails, phone numbers, positions). The 500 handler, the sweeper and about
  20 `err.message` logs printed it. Now `lib/log.ts` logs only the Postgres error code and
  replaces email addresses in other messages.
- **P2: a DNS outage held up the whole sweeper** (SOS retries, check-in and offline alerts):
  `syncDirtyDns` tried every dirty phone with a 10–20 s timeout each. It now stops after three
  failures in a row and takes phones in random order.
- **P2: an older DNS sync could overwrite a newer one and leave the phone marked synced**, so the
  filter ran old rules with nothing retrying. A superseded sync now marks the phone dirty and
  bumps the version.
- **P2: the urgent "protection removed" push waited for one mail per parent**, one after another.
  Push and mails now go out together.
- **P2: no test for reading the attestation record closest to the root.** Added, with a
  self-made chain (`test/fixtures/attestation/make-forged-leaf.sh`), in `server/test/attestation.test.ts`.
- **P2: a failed setup-undo push did not count against the subscription.** It now raises
  `push_subscriptions.failures` like `notifyUsers` (shared `recordFailedPush`), so a Web Push
  endpoint is dropped after 20 failures and its notice with it (`test/setup-safety.test.ts`).
- **P2: one failed offline alert stopped the rest.** `alertOfflinePhones` claims every phone
  first and then notified them in a loop without `try/catch`, so one error cost the other claimed
  phones their alert for good. Each alert is now caught on its own (`test/notifications.test.ts`).

## Fixed on branch `fix/audit-followups`

- **P2: setup-undo notices retried every minute forever.** `setup_undo_notices` has `attempts` and
  `created_at` now. A failed delivery waits 1 minute, then 2, 4 and so on up to an hour, and the
  notice is dropped with one log line (no personal data) once it is a day old
  (`test/setup-safety.test.ts`). Additive migration `0054_audit_followups`.
- **P3: docs said a trusted key waits 24 hours until the helper joins; the code uses the key's own
  delay.** Decision 21/11-26: the key's own delay stays. `docs/self-keys.md` and
  `docs/light-mode.md` now say so, and `test/self-key.test.ts` pins it (1 and 6 hours).
- **Mute.** Decision 21/11-26: quick messages, check-ins and suggestions from the child, and the
  review reminder (push and mail) respect a parent's mute for the phone, but still land in the inbox
  or on the dashboard. SOS, code words and protection-lost alerts always come through
  (`test/mute.test.ts`).
- **Per-minute cleanup scanned all of `summary_events`.** Index `summary_events_at_idx` on `at`
  (same migration).

## Left open

### P3: the device status request still waits for the alert mails

- **Where:** `server/src/services/notifications.ts:241`, called from `server/src/routes/device.ts`
  (`PUT /status`) and `server/src/routes/attestation.ts`
- **Scenario:** the push no longer waits for the mails, but the phone's request does: with SMTP
  hanging, `PUT /api/device/status` takes up to about 35 s (nodemailer's timeouts). The state is
  already saved, so nothing is lost, but the phone sees a timeout.
- **Suggested fix:** send alert mails after the response (or from a queue), with a timeout like the SOS path.

### P3: modes routes answer 500 on a malformed id

- **Where:** `server/src/routes/modes.ts:47-50`
- **Scenario:** `PUT /api/phones/<pid>/modes/------------------------------------` (36 hyphens)
  passes the local regex check; Postgres fails to parse it as a uuid, and the client gets a 500
  with a stack trace in the log.
- **Suggested fix:** use `param()` from `lib/http.ts`, like every other route.

### P3: more than 20 modes per phone under concurrent requests

- **Where:** `server/src/services/modes.ts:158-166`
- **Scenario:** two concurrent `POST /phones/:pid/modes` with 19 modes stored both count 19 and
  both insert. The transaction does not lock the phone row.
- **Suggested fix:** `select … for update` on the phone first, as `setSchedule` does.

### P3: no cap on pending trusted changes or emergency-opening reports

- **Where:** `server/src/services/changes.ts:637` and `server/src/routes/device.ts:922`
- **Scenario:** every loosening on a trusted-key Self phone mails and pushes the helper. A script
  (or another household member) can queue hundreds, and the helper gets hundreds of mails. Each
  `POST /api/device/emergency-openings` with a new id also pushes the helper; that route has no
  rate limit.
- **Suggested fix:** cap open pending changes per phone (for example 50) and batch helper mails;
  add a per-phone `RateLimiter` on emergency-opening reports (the phone stays the authority: record,
  but stop notifying past the limit).

### P3: contact suggestion uploads have no row cap

- **Where:** `server/src/services/contact-suggestions.ts:13`
- **Scenario:** `contacts` and `numbers` have no `.max()`. A 4 MB body holds about 200,000
  numbers, all inserted while the phone row is locked, and `GET /phones/:pid/contact-suggestions`
  returns them unpaged. The phone itself only sends up to 2,000 contacts (docs/privacy.md).
- **Suggested fix:** `.max(2000)` on `contacts` and `.max(10)` on `numbers`.

### P3: removing a Self phone counts as "connected" later than other changes

- **Where:** `server/src/services/changes.ts:176` vs. `:627`
- **Scenario:** `submitChange` treats a phone with a device token as connected, but the
  `phone.remove` loosening check only looks at `pairedAt`. A Self phone that confirmed pairing
  but never synced can be removed at once instead of waiting for its key. The phone has no rules
  from the server yet, so the window gives little.
- **Suggested fix:** use `phone.pairedAt !== null || phone.deviceTokenHash !== null` there too.

### P3: the first login of a new address can fail with a 500

- **Where:** `server/src/services/auth.ts:54`
- **Scenario:** a new user opens two login links at the same time (two tabs, or web and the app).
  Both transactions find no user, and the second insert hits the unique index on `users.email`.
- **Suggested fix:** `insert … on conflict do nothing` on the email, then select the user.

### P3: reset-protection sign-in can be blocked for everyone

- **Where:** `server/src/services/reset-protection.ts:49`, `server/src/routes/reset-protection.ts:50`
- **Scenario:** `PendingLogins` has one global cap of 1,000 and throws a plain `Error` (a 500).
  About 50 throwaway accounts at 20 starts an hour each keep it full, and Google sign-in for reset
  protection fails for every parent.
- **Suggested fix:** cap per user, and answer 429/503.

### P3: the setup-QR retry also works after the phone has synced

- **Where:** `server/src/services/enrollment.ts:111-117`
- **Scenario:** within 60 minutes, the same token and install id get a new device token even after
  the phone synced. That is no longer the "answer got lost" case, and the phone that is in use is
  signed out (401). It needs both the QR token and the install id.
- **Suggested fix:** also require `phone.lastSeenAt === null`.

### P3: attestation verification blocks the event loop

- **Where:** `server/src/services/attestation.ts:141`
- **Scenario:** `spawnSync` runs `openssl verify` (timeout 3 s) inside the request, so every other
  request waits meanwhile.
- **Suggested fix:** async `execFile`/`spawn` with the same stdin piping.

### P3: a removed member's reset-protection account stays

- **Where:** `server/src/routes/parent.ts:471`
- **Scenario:** removing a member keeps their `frp_accounts` row (it only cascades on household or
  user deletion). The Google account id stays, and it comes back if the person is invited again.
- **Suggested fix:** delete the row in the same transaction as the membership.

### P3: a superseded DNS sync does not hold the change receipt back

- **Where:** `server/src/services/dns.ts:83-91`
- **Scenario:** the newer sync has already set `rulesAwaitDns=false` when the older upsert
  overwrites the DNS service with the old block list. The superseded sync marks the phone dirty
  again but leaves `rulesAwaitDns` alone, so the phone applies the new rules and sends its change
  receipt (`phones.ts:461`) while the filter runs the old list until the sweeper's next pass
  (at most a minute).
- **Suggested fix:** decide whether a superseded sync should put the phone back into the "waiting
  for DNS" state. Setting `rulesAwaitDns` there changes the rules document the phone already
  applied, so it is a behaviour change, not a one-line fix.

### P3: rate limiter eviction resets the count of a flooding client

- **Where:** `server/src/lib/http.ts` (`RateLimiter.prune`), used by `GET /api/device/pairings/:id`
- **Scenario:** one IP is over the limit on `ip:<pairingId>`. It sends about 45,000 requests with
  made-up pairing UUIDs (each a key of its own, and the route has no per-IP limit), its own key is
  evicted, and polling continues. Low impact: the poll secret has high entropy. Each made-up id
  still costs one unauthenticated database lookup.
- **Suggested fix:** add a per-IP limit to the poll route, sized for several phones pairing
  behind one carrier NAT. The trade-off is documented on `prune`.

### P3: review reminder mails ignore a parent's mute

- **Where:** `server/src/services/age-review.ts:202-211`
- **Scenario:** the reminder mail goes to every member, including one who muted the phone; the push
  respects the mute, and protection and offline mails exclude muted members.
- **Suggested fix:** build the recipients with `phoneAlertRecipients`.

### P3: quick messages and suggestions notify muted parents

- **Where:** `server/src/services/quick-messages.ts:73-77` (`parentIds`), used at `:134` and `:161`
- **Scenario:** messages from the child ("I'm home") reach every member, also one who muted the
  phone. May be intended (the SMS fallback depends on the `notified` count), but no doc says so.
- **Suggested fix:** decide, and document it in `docs/family-inbox.md` or follow the mute.

### P3: APNs opens a new HTTP/2 connection per notification

- **Where:** `server/src/providers/native-push.ts:75`
- **Scenario:** Apple asks providers to keep connections open; rapid connect and disconnect can be
  treated as abuse and throttled.
- **Suggested fix:** keep one session per origin and reconnect on `goaway`/error.

### P3: summary pruning scans `summary_events` every minute

- **Where:** `server/src/services/weekly-summary.ts:284`
- **Scenario:** the delete filters on `at` alone, but the only index is `(phone_id, at)`, so it is a
  sequential scan on every sweep as the table grows.
- **Suggested fix:** migration: an index on `summary_events(at)` (like `sos_created_idx`).

### P3: smaller performance items

- `server/src/routes/parent.ts:1257`: `/people-i-help` loads each phone and its openings one by one (N+1).
- `server/src/routes/device.ts:552`: `PUT /api/device/apps` upserts up to 1,000 apps one statement at a time.
- `server/src/services/weekly-summary.ts:199-212`: three queries per household on every sweep.
- `server/src/providers/dns.ts:86-90`: response bodies are never read or discarded.
- `server/src/routes/parent.ts:1096` and `:1106`: "update now" and "update apps now" wake the phone
  with no rate limit; a script could wake a child's phone every second.

### P3: no test for clearing `awaitingQrHelper` on a tightening key change

- **Where:** `server/src/services/changes.ts` (`key.set`)
- **Scenario:** the behaviour is right today, but no test guards it.
- **Suggested fix:** add a case to `server/test/self-key.test.ts`.

## Checked and found sound

Session, device-token and enrollment lookups are unique-indexed; `requirePhone`, `requireMember`,
change cancel and `requireTrusted` all join on household membership; every Self-key operation's
loosening check; trusted approval (HMAC revision, single-use QR challenge bound to the helper);
pairing (constant-time poll secret, single claim); server move (single-use tickets and tokens);
attestation (pinned roots, revocation, single-use challenges); mail templates escape every value;
outbound push only to allow-listed hosts with `redirect: "error"` and timeouts; static files are
safe from path traversal; `packages/crypto` checks wire fields strictly and rejects small-order
Ed25519 points and non-canonical signatures.
