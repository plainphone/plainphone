# Server audit, 2026-11-20

Scope: `server/` (routes, services, auth, enrollment, rules, push and mail senders, DNS sync,
rate limits) and `packages/crypto`. The audit looked for authorization and household isolation
holes, input validation, personal data in logs, rate limits, replay, crash paths, slow queries,
unbounded memory, races and untested safety-critical paths.

No P1 finding: no cross-household access, no Self-key bypass, no token or approval replay, and no
way for a child to loosen the rules from the server side was found.

## Fixed on branch `fix/hardening-server`

Each has a test (named below, else in `server/test/hardening.test.ts`) that
fails without the fix.

- **P2: unauthenticated memory exhaustion.** No request body limit, and `RateLimiter` kept every
  key for its whole window (`GET /api/device/pairings/<any string>` added a new key per request).
  Now a 1 MB default body limit on `/api/*` (contact suggestions and server-move import keep their
  own), a key cap in `RateLimiter`, the pairing id checked before the limiter, and the login IP
  limit taken before the body is read.
- **P2: personal data in the server log.** drizzle's `DrizzleQueryError` message holds the
  query's parameters (emails, phone numbers, positions). The 500 handler, the sweeper and about
  20 `err.message` logs printed it. Now `lib/log.ts` logs only the Postgres error code and
  replaces email addresses in other messages.
- **P2: a DNS outage held up the whole sweeper** (SOS retries, check-in and offline alerts):
  `syncDirtyDns` tried every dirty phone with a 10–20 s timeout each. It now stops after three
  failures in a row and takes phones in random order.
- **P2: an older DNS sync could overwrite a newer one and leave the phone marked synced**, so the
  filter ran old rules with nothing retrying. A superseded sync now marks the phone dirty and
  bumps the version.
- **P2: the urgent "protection removed" push waited for one mail per parent**, one after another.
  Push and mails now go out together.
- **P2: no test for reading the attestation record closest to the root.** Added, with a
  self-made chain (`test/fixtures/attestation/make-forged-leaf.sh`), in `server/test/attestation.test.ts`.
- **P2: a failed setup-undo push did not count against the subscription.** It now raises
  `push_subscriptions.failures` like `notifyUsers` (shared `recordFailedPush`), so a Web Push
  endpoint is dropped after 20 failures and its notice with it (`test/setup-safety.test.ts`).
- **P2: one failed offline alert stopped the rest.** `alertOfflinePhones` claims every phone
  first and then notified them in a loop without `try/catch`, so one error cost the other claimed
  phones their alert for good. Each alert is now caught on its own (`test/notifications.test.ts`).

## Fixed on branch `fix/audit-followups`

- **P2: setup-undo notices retried every minute forever.** `setup_undo_notices` has `attempts` and
  `created_at` now. A failed delivery waits 1 minute, then 2, 4 and so on up to an hour, and the
  notice is dropped with one log line (no personal data) once it is a day old
  (`test/setup-safety.test.ts`). Additive migration `0054_audit_followups`.
- **P3: docs said a trusted key waits 24 hours until the helper joins; the code uses the key's own
  delay.** Decision 21/11-26: the key's own delay stays. `docs/self-keys.md` and
  `docs/light-mode.md` now say so, and `test/self-key.test.ts` pins it (1 and 6 hours).
- **Mute.** Decision 21/11-26: quick messages, check-ins and suggestions from the child, and the
  review reminder (push and mail) respect a parent's mute for the phone, but still land in the inbox
  or on the dashboard. SOS, code words and protection-lost alerts always come through
  (`test/mute.test.ts`).
- **Per-minute cleanup scanned all of `summary_events`.** Index `summary_events_at_idx` on `at`
  (same migration).

## Fixed on branch `fix/audit-open-server-clients`

Tests are in `server/test/audit-open.test.ts` unless named otherwise.

- **P3: the device status request waited for the alert mails.** `PUT /api/device/status` and the
  attestation check now send the protection-lost push at once and start the mails after it without
  waiting (`mailsAfterResponse`). Every alert mail has a 10 s timeout. The push is not delayed and
  not rate limited. The sweeper still waits for its mails.
- **P3: modes routes answered 500 on a malformed id.** They use `param()` now (404).
- **P3: more than 20 modes under concurrent requests.** `createMode` locks the phone row first.
- **P3: no cap on pending trusted changes.** At most 50 open changes per phone (429 past that).
  The trusted person gets one mail and one push per hour, however many requests are queued; every
  request still shows in their approvals list. SOS, 112 and protection-lost alerts do not go
  through this path.
- **P3: no rate limit on emergency-opening reports.** Every report is still recorded (the phone is
  the authority); the trusted person is pinged for at most 20 an hour per phone.
- **P3: contact suggestion uploads had no row cap.** At most 2,000 contacts and 100,000 numbers,
  the phone's own limits. The audit's `.max(10)` per contact was not used: the phone sends complete
  contacts, and an existing test pins that a contact with more than 100 numbers is accepted.
- **P3: removing a Self phone counted as "connected" later than other changes.** It checks the
  device token as well now.
- **P3: the first login of a new address could fail with a 500.** `insert … on conflict do nothing`,
  then the user is selected.
- **P3: reset-protection sign-in could be blocked for everyone.** Each account holds at most 3
  places (an older start of the same account gives way), and a full table answers 503, not 500.
- **P3: the setup-QR retry also worked after the phone had synced.** It needs `lastSeenAt` to be
  empty.
- **P3: attestation verification blocked the event loop.** `openssl verify` runs through async
  `execFile` (`verifyAttestation` is async now); `test/attestation.test.ts` awaits it.
- **P3: a removed member's reset-protection account stayed.** It is deleted with the membership.
- **P3: rate limiter eviction reset the count of a flooding client.** The pairing poll route has a
  per-address limit of 3,000 an hour, as well as the per id one.
- **P3: "update now" and "update apps now" had no rate limit.** 30 an hour per phone and kind (429).
- **P3: `PUT /api/device/apps` upserted one statement per app.** One statement per 500 apps.
- **P3: DNS provider response bodies were never read or discarded.** They are discarded.
- **P3: no test for clearing `awaitingQrHelper` on a key change.** Added.
- **Already fixed by #203:** review reminder mails ignore a parent's mute (now follow it), quick
  messages and suggestions notify muted parents (decision: follow the mute), summary pruning scan
  (index `summary_events_at_idx`).
- **Claim and enroll pick an arbitrary household** (clients audit): a parent in more than one
  household must send `householdId`, else 400. Both clients send it.

## Left open

### P3: APNs opens a new HTTP/2 connection per notification

- **Where:** `server/src/providers/native-push.ts:75`
- **Why it stays open:** keeping one session per origin and reconnecting on `goaway` changes the
  delivery path of every iOS parent push, SOS included. It cannot be tested against a real APNs
  here, and a stale session would turn into failed pushes. It needs a test on a real device and its
  own change.
- **Suggested fix:** keep one session per origin and reconnect on `goaway`/error.

### P3: a superseded DNS sync does not hold the change receipt back

- **Where:** `server/src/services/dns.ts:83-91`
- **Why it stays open:** setting `rulesAwaitDns` there changes the rules document the phone already
  applied, so it is a behaviour decision, not a fix (at most a minute of the old filter list).
- **Suggested fix:** decide whether a superseded sync should put the phone back into the "waiting
  for DNS" state.

### P3: smaller performance items

- `server/src/routes/parent.ts` (`/people-i-help`): one query pair per phone, run in parallel. A
  helper helps a handful of people, so it was left as it is.
- `server/src/services/weekly-summary.ts:199-212`: three queries per household on every sweep. No
  measurement shows a problem; left.

## Checked and found sound

Session, device-token and enrollment lookups are unique-indexed; `requirePhone`, `requireMember`,
change cancel and `requireTrusted` all join on household membership; every Self-key operation's
loosening check; trusted approval (HMAC revision, single-use QR challenge bound to the helper);
pairing (constant-time poll secret, single claim); server move (single-use tickets and tokens);
attestation (pinned roots, revocation, single-use challenges); mail templates escape every value;
outbound push only to allow-listed hosts with `redirect: "error"` and timeouts; static files are
safe from path traversal; `packages/crypto` checks wire fields strictly and rejects small-order
Ed25519 points and non-canonical signatures.
