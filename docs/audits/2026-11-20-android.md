# Android hardening audit, 2026-11-20

Scope: the phone app in `android/` (policy enforcement, Device Owner and light-mode guard, sync,
calls and messages, SOS, maintenance windows, emergency openings, modes). Not the server.
Method: code reading with concrete scenarios against [bypass-checklist.md](../bypass-checklist.md).
Every finding below was checked in the code. Most could not be tried on a phone.

Ratings: **P1** security hole, data leak across households, a child can bypass protection, or
data loss. **P2** wrong behaviour a user will hit, or a missing test on a safety-critical path.
**P3** minor.

## Fixed in this branch

Each fix has a test that fails on `main`. The only exception is the PIN lockout test in
`ClockTrustTest`, which uses the new boot-clock parameter and does not compile on `main`.

| Rating | Finding | Fix |
|---|---|---|
| P1 | An urgent SOS neither texted nor called the parents when the server answered 4xx (for example 403 after a release in the dashboard that the phone has not synced yet) | `sos/SosDelivery.kt`: a refused report still sends the SMS fallback and starts the call |
| P1 | A phone marked removed, or whose token cannot be opened, lost the whole SOS, including the call | Same place: without a token the report is skipped, but the SMS and call still go out |
| P1 | Light mode: a parent's maintenance unlock stayed open after force stop plus setting the date back, until the next reboot | `Lock.kt` + `BootClock.kt`: the unlock also ends on the time since boot and at a reboot |
| P2 | Any 401 on GET `/device/rules` (for example from a proxy in front of a self-hosted server) unpaired the phone for good | `sync/PlainphoneApi.kt`: only `unknown device; pair again` unpairs |
| P2 | Light mode: setting the clock forward ended the PIN lockout | `PinThrottle.kt`: the lockout also runs on the time since boot, and is capped at an hour if the clock is set back |
| P2 | Any app declaring a camera, alarm, contacts, Settings, dialer, home or SMS filter counted as core: never hidden, never closed by the guard, never time-limited | `DeviceControls.kt`: only system apps for those filters, plus the chosen phone app, home screen, SMS app, keyboard and Plainphone |
| P2 | Light mode: a block within 700 ms of the previous one was dropped with no retry, so a quick switch back kept a blocked app open | `light/GuardService.kt`: the dropped block is retried when the gap ends, and the 30 s tick re-checks the allow-list |
| P2 | Light mode: a guard that restarted (crash, update) did not check the app already in front | Same file: `onServiceConnected` checks the active window |
| P2 | Light mode: the 5 s time-limit check was shared across apps, so switching apps could skip a used-up app for up to 30 s | Same file: the throttle is per app |
| P2 | Light mode: with the clock set by hand, school time and bedtime follow it (see the open finding below) | `light/LightLock.kt`: the step "automatic date and time" fails when school time, bedtime or limits depend on the clock, so the parent sees it |
| P2 | No tests for the SMS receiver, SMS sender and emergency call-back window wiring | `telephony/SmsScreeningTest.kt` |
| P3 | A last apply "in the future" (the clock set back since) counted as fresh, so a failed private DNS step was not retried | `Lock.applyIfNeeded`: a negative age is not fresh |
| P1 | (review) The system-app filter above also shrank the SMS apps hidden while Plainphone holds the SMS role, so an SMS app from Play became visible when Messages was allowed (C12) | `DeviceControls.kt`: only `corePackages()` filters SMS apps to system apps; `telephonyApps()` lists all |
| P2 | (review) After a refused SOS the SMS went out, but the server was never told, so the SOS was missing from the dashboard and push | `sos/SosDelivery.kt`: the phone reports once more with `smsSubmitted`, which the server always records |
| P3 | (review) A clock set back stretched a 1-minute PIN lockout to the full hour | `PinThrottle.kt`: within the same boot only the boot clock counts |

## Open findings

The first pass left some findings open. #205 (`fix/trusted-clock`) fixed the clock P1, the
emergency-month P2 and the catalog daily-limit P3. #206 (`fix/android-audit-open`) fixed the rest
that is small and safe, and says below why the others stay open. The picture-in-picture P1 is
fixed in code but still has to be confirmed on a physical phone.

### Light mode trusts the wall clock for school time and bedtime (P1, fixed in this PR)

- **Where:** `sync/EffectivePolicy.kt` (windows evaluated with `Instant.now()`), `Lock.effectiveConfig` (`Lock.kt:161`), and the RTC window alarm in `Lock.scheduleNextWindowChange`.
- **Scenario:** at bedtime the child turns off automatic time and sets the clock to 07:05. The next apply sees no active window, and the apps open again.
- **Now:** the step "automatic date and time" fails, so the parent sees it (fixed above). The bypass itself remains.
- **Suggested fix:** a `TrustedClock`. It takes the server's `Date` at each sync, adds `elapsedRealtime` since then, and resets on a new boot count. Schedules, emergency months and the catalog daily limit then use it. The design question is the fallback when the phone has not synced since boot: fail closed (treat the window as active) or trust the wall clock. Decide that before implementing.
- **Fixed in this PR** (`fix/trusted-clock`): `time/TrustedClock.kt` keeps the server's time (`X-Server-Time`) on the boot clock. After a restart without a sync it is cautious, as decided on 20/11-26: from the last known time, every window that may be on counts as on ([light-mode.md](../light-mode.md#the-phones-clock)). The window alarm runs on the boot clock.

### Emergency openings refill when the clock is set forward a month (P2, fixed in this PR)

- **Where:** `light/EmergencyOpenings.kt:128` (`usedThisMonth`).
- **Scenario:** a Self user spends all openings in November and sets the clock to December. The local count is 0, and the server's November count is ignored, so the openings are available again. This repeats every month. The 15-minute window itself is safe, because it uses the boot clock, and the trusted person is still told.
- **Why not fixed:** counting against the server's month would make the count stale at a real month change until the next sync. Existing tests require the opposite ("A server count for October says nothing about November").
- **Suggested fix:** use the `TrustedClock` above for the month key.
- **Fixed in this PR:** the month key, the opening time and the pruning use the trusted time. The existing tests with an injected clock are unchanged.

### A blocked video app can keep playing in picture-in-picture (P1, fixed in #206, confirm on a phone)

- **Where:** `light/GuardService.kt`, `block()` and the `TYPE_WINDOWS_CHANGED` branch of `onAccessibilityEvent`.
- **Scenario:** `block()` sends Home first. A video app that was playing (for example when its time runs out) enters picture-in-picture on Home. Entering picture-in-picture only produces `TYPE_WINDOWS_CHANGED`, which the guard uses for its Settings watch, never for apps. The video keeps playing in a small window.
- **Suggested fix:** on `TYPE_WINDOWS_CHANGED` and on each tick, look for a window in picture-in-picture mode whose root package has a non-null `LightPlan.why` and no active emergency opening. Dismiss it, as SystemUI's picture-in-picture menu does, or start the stop screen over it. First confirm the behaviour on a physical phone.
- **Fixed in #206:** `light/PipGuard.kt` decides, `GuardService.guardPip()` acts. On every windows-changed event, every 30 s tick and every dropped-block retry it looks for windows in picture-in-picture mode whose root package the plan blocks (not allowed, or time used up) and that no emergency opening covers. It sends `ACTION_DISMISS` to the window's root and shows the stop screen, which also sends Home. The live time check runs for picture-in-picture apps too, so a limit that runs out while a video floats is caught. Robolectric tests cover the decision and the service. **Not confirmed on a phone:** whether `ACTION_DISMISS` closes SystemUI's picture-in-picture window on every maker; if not, the stop screen is shown over it and the audio may keep playing. Steps are in [bypass-checklist.md](../bypass-checklist.md) (L-T8, L-T9).

### The PIN lockout check and the failure record are not atomic (P3, fixed in #206)

- **Where:** `MaintenanceActivity.kt:99` and `requests/ParentPinCheck.kt`.
- **Scenario:** `remainingMs()` is read before the slow PIN check, and the failure is recorded after it. Rotating the screen or using split screen with the requests screen gives a few extra guesses at each lockout boundary.
- **Suggested fix:** record a pending failure before verifying and clear it on success, or put the check and verify behind one process-wide lock.
- **Fixed in #206:** `PinThrottle.attempt` does the lockout check, the verify and the record under one process-wide lock; the maintenance screen and the requests screen both use it. A test starts two checks at a lockout boundary and sees one guess.

### The phone-app-changed receiver accepts broadcasts from any app (P3, fixed in #206)

- **Where:** `RoleWatcher.kt:48` (`RECEIVER_EXPORTED`).
- **Scenario:** any installed app can send `ACTION_DEFAULT_DIALER_CHANGED` in a loop. Each broadcast forces a full apply and a sync, which drains battery and data.
- **Suggested fix:** debounce, for example at most one apply per 30 s.
- **Fixed in #206:** `Debounce` (used by `RoleWatcher`): the first broadcast applies at once, later ones inside 30 s fold into one trailing run, so the last change is kept. The receiver stays exported because Telecom sends the broadcast.

### Light-mode catalog daily limit uses the wall-clock date (P3, fixed in this PR)

- **Where:** `catalog/InstallWindow.kt:81` (`LocalDate.now()`).
- **Scenario:** changing the date resets the limit of 5 Play windows per day. Only parent-approved apps can open a window.
- **Suggested fix:** use the `TrustedClock` above.
- **Fixed in this PR:** the day and the window's end use the trusted time.

### Install watchdog retries every second when recovery keeps failing (P3, fixed in #206)

- **Where:** `update/InstallWatchdogService.kt:95` (`onDeadline`).
- **Scenario:** if `recover()` throws every time, the watchdog retries every second until its wakelock cap (about 45 minutes).
- **Suggested fix:** exponential backoff, starting at 1 s and capped at 1 min.
- **Fixed in #206:** `onDeadline` doubles its retry delay from 1 s to 1 min.

### Idle DNS-over-TLS connections are closed only on the next use (P3, fixed in #206)

- **Where:** `light/vpn/DotResolver.kt`, connection pool (`idleTimeoutMs`).
- **Scenario:** after a burst of lookups, up to 4 TLS sockets stay open while nothing is looked up. [light-mode-vpn.md](../light-mode-vpn.md) says they close after 30 s idle.
- **Suggested fix:** sweep expired connections on a timer, or set a socket idle timeout.
- **Fixed in #206:** a daemon timer sweeps expired idle connections (`DotResolver.sweepIdle`) after the idle time.

### Large DNS answers cannot be resolved through the VPN (P3, stays open)

- **Where:** `light/vpn/DnsPackets.kt` (truncated answers) and `light/vpn/PacketPolicy.kt`.
- **Scenario:** answers over 1,472 bytes come back with the TC flag. The resolver retries over TCP to the tunnel's DNS address, and the tunnel drops that. This fails closed, but some large TXT and DNSSEC lookups break.
- **Suggested fix:** answer DNS over TCP inside the tunnel, or advertise a larger EDNS buffer when the tunnel MTU allows it.
- **Why it stays open:** it needs a TCP stack inside the tunnel (or MTU and fragmentation work), which is a feature, not a small fix, and cannot be tried without a phone. It fails closed.

### VPN timing uses the wall clock (P3, fixed in #206)

- **Where:** `light/vpn/PacketForwarder.kt` and `DotResolver.kt` (`nowMs = System::currentTimeMillis`).
- **Scenario:** a clock change in light mode can mark every queued query as stale, or keep idle connections forever.
- **Suggested fix:** use `SystemClock.elapsedRealtime`.
- **Fixed in #206:** `PacketPolicy` and `DotResolver` default to `SystemClock.elapsedRealtime`.

### "Overlay" packages are matched by substring (P3, fixed in #206)

- **Where:** `light/GuardService.kt:367` (`isOverlay`).
- **Scenario:** any app whose package name contains `inputmethod` is treated as the keyboard. It never becomes "the app in front" and never gets live time-limit checks.
- **Suggested fix:** compare against the enabled input methods from `InputMethodManager`.
- **Fixed in #206:** the guard compares with the enabled input methods (plus the stock AOSP keyboard package) and SystemUI.

### One unknown request kind empties the requests list (P3, fixed in #206)

- **Where:** `requests/PhoneRequest.kt:74` (`parseList`).
- **Scenario:** a newer server adds a request kind or status. Older phones throw while parsing, and the Requests screen is empty.
- **Suggested fix:** skip entries that cannot be parsed instead of failing the whole list.
- **Fixed in #206:** `parseList` skips unreadable entries. A body that is not a request list at all is still an error, never an empty list.

### The rule checks the normalised number, but the typed number is dialled (P3, fixed in #206)

- **Where:** `ui/PhoneActivity.kt:178` (`placeCall`) and `SmsSender.send` in `telephony/Sms.kt`.
- **Scenario:** the QR code says +45 but the SIM is Norwegian. The child types `12345678`, which matches the approved `+4512345678`, but the network dials the Norwegian `12345678`. The child cannot freely choose the target.
- **Suggested fix:** once the rule allows it, dial or send the normalised number.
- **Fixed in #206:** `placeCall` and `SmsSender.send` use the approved contact's number when the rule matched one. Emergency numbers and help lines are unchanged.

### Outgoing calls fail open when the rules cannot be read (P3, fixed in this PR)

- **Where:** `telephony/PlainphoneInCallService.kt:51` and `PlainphoneCallRedirectionService.kt`.
- **Scenario:** if reading the rules throws, a non-emergency outgoing call is allowed. This is deliberate, and emergency calls do not depend on it. The child cannot trigger the exception today.
- **Suggested fix:** fail closed for non-emergency outgoing calls, keeping parents and emergency numbers reachable through the stored list.
- **Why it stays open:** there is no second copy of the parents' numbers that does not go through the same `rules()` read. Failing closed on an exception would also block the child's calls to the parents, which must stay reachable, and the child cannot trigger the exception. Fix it together with a separate, always-readable parent list (for example one stored beside the emergency numbers).
- **Fixed in this PR:** `contacts/ParentNumbers.kt` keeps a separate copy of the parents' numbers in device-protected storage, rewritten whenever the rules are put together. When the rules read throws, `UnreadableRules` allows 112, the emergency numbers and that list, and ends every other outgoing call with a calm message, in both the in-call service and the call redirection service. Without the list (first boot, never synced) calls stay open, as before. It is a failsafe with no per-phone switch, because a switch would live in the rules that cannot be read. Tests: `FailsafeTest`. Steps for a phone: [bypass-checklist.md](../bypass-checklist.md) (C20).

### An exception while receiving an SMS loses the message (P3, fixed in this PR)

- **Where:** `telephony/Sms.kt:259` (`SmsDeliverReceiver`).
- **Scenario:** if `rules()` or the decision throws, the receiver crashes. Only the default SMS app stores messages, so the message is gone, including one from a parent.
- **Suggested fix:** catch the exception, and store the message as blocked, or hold it for review, instead of dropping it.
- **Why it stays open:** there is no "held for review" store, and storing the message as normal would show a stranger's text to the child when the rules cannot be read. It needs that store (a product decision), and the child cannot trigger the exception.
- **Fixed in this PR:** `telephony/HeldSms.kt` is the held-for-review store: sealed with a keystore key, outside the system's message store, no notification. When handling throws, `SmsFailsafe` delivers a message from a number in the parents' copy as usual and holds every other one. The parents read, delete or clear them on the PIN-protected maintenance screen, with the blocked log's retention (newest 100) and a 30-day age limit. A message that was already stored is not held twice. Tests: `FailsafeTest`. Steps for a phone: [bypass-checklist.md](../bypass-checklist.md) (C21).

### Quick messages give up on 408 and 429 (P3, fixed in #206)

- **Where:** `sos/QuickMessageDelivery.kt:44`.
- **Scenario:** a timeout or rate limit from a proxy counts as `GIVE_UP` instead of retry or SMS fallback.
- **Suggested fix:** treat 408 and 429 like 5xx.
- **Fixed in #206:** `quickMessageFallback` sends the SMS fallback for 408 and 429.

### Residual risks of this branch's fixes (P3)

- **The PIN lockout after a reboot runs on the wall clock only.** In light mode a reboot followed by setting the clock forward still ends a lockout. A reboot takes about a minute, so this gains little.
- **The emergency dialer action stays open to any handler.** An app that declares `com.android.phone.EmergencyDialer.DIAL` still counts as core. This was left as is so that emergency calls never depend on a package check.
- **In light mode the child can choose a sideloaded launcher as the default home screen.** The chosen home screen counts as core. The guard still closes the apps it launches.
