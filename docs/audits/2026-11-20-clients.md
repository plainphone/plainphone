# Client audit, 20 November 2026: web dashboard, parent app and site

Scope: `web/`, `parent-app/` and `site/`. The server and Android were out of scope, but three
server findings came up while tracing client flows; they are listed at the end.

Fixed on branch `fix/hardening-clients`, each with a test that fails without the fix:

The findings below are not fixed.

## Server: claim and enroll pick an arbitrary household

- **Where:** `server/src/routes/parent.ts:513` (`myHouseholdIds`), used at `:579` (`/phones/claim`) and `:638` (`/phones/enroll`).
- **Scenario:** a parent in two households claims a phone with an older client that sends no `householdId`. `hids[0]` comes from a query without `ORDER BY`, so the phone can go into either household, including one the parent joined through an invitation.
- **Suggested fix:** order by `households.createdAt` like `GET /me`. Better, answer 400 when the parent has more than one household and no `householdId` was sent. Both clients now send it.

## Server: an invitation can be accepted by any account

- **Where:** `server/src/routes/parent.ts:430` (`POST /invites/accept`).
- **Scenario:** an invitation is sent to one address, and the link is forwarded or sent to another person on purpose. That person's account joins the household, whatever its email. The clients now ask before joining, but they can't name the household or the inviter.
- **Suggested fix:** accept only when the signed-in email matches the invited address (case-insensitive). Alternatively, add a preview endpoint that returns the household name and the inviter's email, so the confirmation can name them.

## Server: login links are not bound to the device that asked for them

- **Where:** `POST /auth/request` and `POST /auth/verify`.
- **Scenario:** the clients now ask before using a link they did not request. A parent who taps **Log in** anyway is still signed into the sender's account.
- **Suggested fix:** let the client send a random nonce with `/auth/request`, keep it locally, and require it in `/auth/verify`. A link opened on another device then falls back to a typed code.

## Web: an expired session leaves browser push bound to the old account

- **Where:** `web/src/lib/session.tsx:116` (the unauthorized handler).
- **Scenario:** parent A's session expires on a shared browser, and parent B signs in without opening Notifications. The browser keeps getting A's alerts, including SOS with the child's name. Only an explicit logout unsubscribes.
- **Suggested fix:** after login, compare this browser's subscription (`pp_push_id`) with the new account's list. If it belongs to someone else, unsubscribe it or say so on the Notifications page.

## Web: account deletion does not unsubscribe the browser

- **Where:** `web/src/pages/Settings.tsx:46`.
- **Scenario:** the server deletes the subscription rows, but the browser's push subscription stays registered with the push service until the next failed send.
- **Suggested fix:** call `disablePush` before `DELETE /me`, the same way logout does.

## Web: the pairing code stays in the address bar

- **Where:** `web/src/pages/Pair.tsx:15`.
- **Scenario:** `/pair?code=…` stays in history after pairing. The code is short-lived and the phone confirms the pairing, so the risk is low.
- **Suggested fix:** `replaceState` once the code has been read, like the other token pages.

## Web: a notification URL can leave the app's origin

- **Where:** `web/public/sw.js:199`.
- **Scenario:** `new URL(data.url, origin)` accepts `//other.example/x`. Only the server can send pushes, and it builds every URL itself, so this would take a server bug.
- **Suggested fix:** open the URL only when its origin equals `self.location.origin`, otherwise open `/`.

## Parent app: some safety-critical buttons guard double taps with state only

- **Where:** `parent-app/src/app/phones/[pid]/key.tsx:65` (`shareInvite` has no guard and creates two trusted-person invitations on a double tap), `key.tsx:74` (save key), `parent-app/src/app/phones/[pid]/index.tsx:337` (remove phone), `parent-app/src/components/SosPanel.tsx` (**I've seen it**).
- **Scenario:** two taps inside one frame both fire, because `Pressable` is disabled only after the re-render.
- **Suggested fix:** a `useRef` guard as in `parent-app/src/app/approvals.tsx`.

## Parent app: an accepted invitation is remembered for the whole process

- **Where:** `parent-app/src/app/invite.tsx:18` (`inflight`).
- **Scenario:** user A accepts invitation X, logs out, and user B opens X in the same app session. B sees "accepted" from A's cached result and no request is made.
- **Suggested fix:** delete each entry once it has resolved, or clear the map on logout.

## Parent app: a logout that failed is retried only at start-up

- **Where:** `parent-app/src/lib/session.tsx` (`retryPendingLogouts` at start).
- **Scenario:** the app stays open in the background for days after an offline logout. The old session stays valid until the app is started again.
- **Suggested fix:** also retry when `AppState` turns `active`.

## Both clients: parents in several households can't choose one

- **Where:** `web/src/pages/Household.tsx:17`, `web/src/pages/Summary.tsx:22`, `parent-app/src/app/household.tsx:22`, `parent-app/src/app/summary.tsx:22`, and the claim and enroll calls.
- **Scenario:** a parent in two households sees, and adds phones to, only the first one.
- **Suggested fix:** a household picker when `me.households.length > 1`, defaulting to the first household.

## Site: no check that new links opened in a new tab carry `rel="noopener"`

- **Where:** `site/scripts/check.mjs`.
- **Scenario:** a future link with `target="_blank"` and no `rel` passes the check. Modern browsers imply `noopener`, so the impact is low.
- **Suggested fix:** in the tag loop, fail when `target="_blank"` and `rel` lacks `noopener`.

## Site: a translation without `{STATUS_LINK}` fails silently

- **Where:** `site/build.mjs:483`.
- **Scenario:** a translator drops the placeholder. The status link then renders as an `<a>` without `href`, and the check does not notice.
- **Suggested fix:** throw in the build when `statusText` lacks `{STATUS_LINK}`.

## Site: a partly typed domain shows "no results" while typing

- **Where:** `site/src/app-search.mjs:15`.
- **Scenario:** typing `youtube.c` on the way to `youtube.com` shows the empty state, because a query with a dot must match the whole value.
- **Suggested fix:** use prefix matching on a dotted query, or show the empty state only after the input settles. Keep the test that `youtube.com.example.org` does not match.

## Site: the menu and language popups do not close on Escape

- **Where:** `site/build.mjs:129`.
- **Scenario:** a keyboard user opens the language list and Escape does nothing. The site has no JavaScript for it.
- **Suggested fix:** a few lines in the existing script that close an open `<details>` on Escape and return focus to its `<summary>`. Update the CSP hash.

## Both clients: Remove and Leave in the household lose focus

- **Where:** `web/src/pages/Household.tsx:154`, `parent-app/src/app/household.tsx:160`.
- **Scenario:** a screen-reader user presses "Remove x". The button unmounts and the question renders in its place, so focus falls back to the page body and the question is not read out.
- **Suggested fix:** move focus to the question (or its "Yes, remove" button) when the confirmation opens, and back to the Remove button on Cancel.

## Parent app (web build): the login token stays in the address bar while the app asks

- **Where:** `parent-app/src/app/auth/app.tsx:58`.
- **Scenario:** on Expo web, a login link that needs confirmation keeps `#token=…` in the URL and history while "Log in with this link?" waits. The web dashboard drops it at once.
- **Suggested fix:** keep the token in state when it is first read and call `replaceState` then, as `web/src/pages/AuthCallback.tsx` does. Today the screen reads the token from `window.location` on every render, so dropping it early needs that change first.

## Parent app: pending logouts for a server that never answers are kept forever

- **Where:** `parent-app/src/lib/pending-logout.ts:45,64`.
- **Scenario:** a parent logs out offline from a self-hosted server that is later removed. The entry, with its bearer token, stays in secure storage and is retried at every start.
- **Suggested fix:** store when the logout was queued and drop entries older than the session lifetime.
