# Web filtering alongside another Android VPN

Research date: **2026-11-18**. Plainphone baseline: `d8bf1c6`. **Source-verified** means repository code, upstream code or official documentation was inspected. **Tested** means a command was run. **Expected** means an inference to verify on a phone before making a compatibility claim. Living sources were consulted on the research date. No accounts were created.

## Android and Tailscale

**Source-verified.** Android allows one active VPN per user or profile. A second VPN replacing Plainphone's light-mode tunnel stops its DNS interception. Plainphone strong mode sets global strict Private DNS through the Device Owner and applies the VPN configuration restriction. Light mode can ask the user to configure the same hostname in Android Settings without holding the VPN slot. [Android VPN guide][vpn] · [Light-mode tunnel](../light-mode-vpn.md) · [Strong-mode policies](../policies.md)

**Source-verified on AOSP main.** Strict mode selects a named provider. ConnectivityService distributes that setting to eligible networks, NetworkMonitor resolves the provider hostname in that network's context, and DnsManager stores the configuration and validation status by network ID. The eligibility check considers Internet capability and trust/restriction capabilities and does not exclude a network merely because its transport is VPN. AOSP's VPN agent advertises Internet capability. The VPN's advertised DNS IPs and routes can affect provider bootstrap and reachability. The DNS IPs do not simply replace the named provider for an eligible network's strict system lookups. If the provider cannot validate, those lookups can fail. Android versions, OEM networking changes, per-app routing, resolver exclusions and VPN-internal DNS can produce different results. Consequently, strict Private DNS can work with a VPN that supplies DNS, but neither the device-wide setting nor an underlying Wi-Fi observation establishes filtering inside the tunnel. [ConnectivityService][cs] · [Eligibility check][eligibility] · [NetworkMonitor][monitor] · [DnsManager][dnsmanager] · [AOSP VPN][aospvpn]

| Android with Plainphone strict Private DNS | Evidence and expected result |
| --- | --- |
| No VPN | Expected baseline. System lookups use Plainphone when the provider resolves and validates on the active network. |
| Tailscale connected, **Use Tailscale DNS settings off** | Best first trial. Tailscale opts the device out of tailnet DNS. Plainphone may work if the VPN routes the provider correctly. The same upstream issue has 2024 and 2025 reports of failure even with this setting off. Expect Tailscale IP routes to remain available and MagicDNS names to be unavailable through Tailscale DNS. Test both tailnet MagicDNS states and exit-node behavior. |
| Tailscale DNS on, MagicDNS on | Tailscale maintainers documented Android sending DNS to the local Tailscale resolver for MagicDNS and conflicts with strict Private DNS. Expect possible loss of tailnet names even when public lookups work, or DNS failure if provider bootstrap or reachability fails. The report spans multiple releases and does not establish current behavior for every device. |
| Tailscale DNS on, MagicDNS off | Turning off MagicDNS alone does not opt out of global override or split DNS. Test with no global override and with an override. Expect the VPN DNS configuration still to matter if Tailscale supplies one. |
| Tailscale DNS on, Android Private DNS Automatic, tailnet upstream forwards to Plainphone | Candidate for keeping MagicDNS and filtering public DNS together. The forwarder, not Android's strict setting, provides Plainphone filtering for requests it forwards. Check exit-node DNS and any app exclusions separately. |
| Company VPN | Expect strict mode to work only on eligible system DNS paths that can bootstrap and reach the provider. Corporate tunnel DNS, private zones, forced proxies and split routing can change effective coverage or break internal names. |

Tailscale's Android client passes configured nameserver IPs to the VPN builder. Its documentation distinguishes MagicDNS, accepting tailnet DNS on a device, global override and DNS with exit nodes. The maintainer discussion in issue #915 (2020–2024 comments) records DNS breakage, including a 2024 maintainer finding that Android bound DoT traffic to a VPN interface with no matching route when no exit node was in use. Tailscale closed the issue as not planned on 2024-10-08. The thread also records the recommendation to let Tailscale own DNS with a supported secure upstream when MagicDNS is required. [Tailscale DNS reference][tsdns] · [Android client source][tsandroid] · [Maintainer reports][ts915]

## Resolver addresses and integrations

**Source-verified.** The checked-in DNS stack serves **DoT only** publicly. Compose exposes TCP 853. The generated AdGuard Home configuration sets `port_https: 0`, and port 53 is internal. The management API is separate. Each phone is provisioned as an AdGuard persistent client. The random ClientID is the leftmost label of the DoT hostname and is sent as TLS Server Name Indication (SNI). The same hostname must be used for TLS certificate verification. An IP alone loses that identifier. Treat the hostname as a shareable resolver credential with a limited audience. Sharing it applies the same policy to other clients and does not identify which device made a request. Keep it out of analytics, notifications and diagnostic logs. [Compose](../../dns/compose.yaml) · [Generated configuration](../../dns/ppdns/config.py) · [Client provisioning](../../dns/ppdns/profiles.py) · [AdGuard ClientIDs][aghclients]

**Tested on 2026-11-18.** A certificate-verified TLS handshake to `dns.plainphone.org:853` succeeded. Using `ppdns.dot.query` for `example.com` returned DNS `REFUSED` for both the base name and an unregistered wildcard hostname, confirming the service answers DoT and rejects these identities. No registered phone profile was used in the live probe. An HTTPS request to the base name on port 443 failed certificate verification, so it does not establish an application-level response from a DoH endpoint. The deployment checked into this repo is the evidence for supported protocols.

| Destination | What to enter |
| --- | --- |
| Android Private DNS provider hostname | `<id>.dns.plainphone.org`, with no scheme or port. |
| Router or VPN with an encrypted DoT upstream | Hostname `<id>.dns.plainphone.org`, TCP `853`, with the same hostname for TLS authentication/SNI. Use `tls://<id>.dns.plainphone.org:853` only where the client documents this URI syntax. |
| Plain DNS IP field or DoH-only field | No Plainphone endpoint today. |
| Future Plainphone DoH | Proposed `https://dns.plainphone.org/dns-query/<id>`. AdGuard Home supports URL-path ClientIDs, but Plainphone must deploy, test and advertise this endpoint first. |

**Tailscale admin console.** Global nameservers plus **Override local DNS** can direct DNS-accepting tailnet clients to a DNS forwarder reachable at a tailnet IP. Configure that forwarder to use the phone's DoT upstream, with TLS verification and no unfiltered public fallback for covered requests. Keep the forwarder private and leave MagicDNS and intentional split zones in Tailscale. A single global forwarder and upstream selects one Plainphone policy for all clients using it, so use a dedicated tailnet or an administrator-managed resolver design that deliberately selects policies per client. Do not paste the DoT hostname or the resolver's IP into the custom nameserver field. The published UI supports IP nameservers and specific encrypted-provider integrations. Arbitrary DoH URL support is still an open console request (#15724, opened 2025), so shipping DoH alone would not make Plainphone a direct Tailscale entry. Console access was not tested. Check the per-device DNS preference and the nameserver's **Use with exit node** setting when relevant. [Tailscale DNS reference][tsdns] · [Custom DoH request][tsdoh] · [NextDNS integration][tsnext]

**Company VPN and router.** Ask IT whether the client or corporate resolver can forward public lookups over DoT while keeping internal zones on company DNS. If the VPN accepts only DNS IPs, the compatible route is a trusted IT-managed forwarder, provided the company approves sending those public queries to Plainphone. Cisco Secure Client for Android is an example of a product with administrator-controlled DNS and split DNS. Its support for those settings does not demonstrate native custom DoT support. For a home router, choose a DoT upstream and verify a blocked and allowed domain from a connected client. Router DNS applies only on that network and only to requests that use it. A full-tunnel VPN, mobile data or an app's resolver can take a different path. [Cisco mobile feature guide][cisco] · [Cisco DNS policy guide][ciscodns]

## How other filters coexist

| Product | Documented approach |
| --- | --- |
| NextDNS | Android can use the profile hostname in system Private DNS. Tailscale offers a native NextDNS DoH integration, including optional policy attributes for selected nodes. With Tailscale owning DNS, its maintainer recommends avoiding simultaneous strict Android Private DNS for this setup. [NextDNS Android support discussion][nextandroid] · [Tailscale launch, 2022-10-12][nextlaunch] · [Tailscale setup][tsnext] · [Maintainer report][ts915] |
| AdGuard | AdGuard DNS documents per-device Android Private DNS hostnames and flags VPN compatibility limits. The AdGuard Android filter ordinarily occupies the VPN slot. Its integration with AdGuard VPN places both functions into a coordinated setup. This is a vendor-specific integration. [Android setup][adgdns] · [AdGuard VPN integration][adgvpn] |
| Control D | Recommends Android's Private DNS with an endpoint-specific hostname. Its optional Android setup utility filters DNS through Android's VPN service and therefore uses the same slot. Tailscale also offers a native Control D integration for personalized DNS. Its separate `ctrld` DNS Intercept Mode addresses VPN DNS conflicts on a host running that service. ## Product design

### Myself in light mode

Keep the existing Plainphone VPN as the default. At filter setup or from **Web filter**, offer **Use with another VPN**. If a VPN transport is visible and Plainphone's own tunnel is inactive, surface that action first. Keep the choice available when an app is excluded from a split VPN and cannot see its transport. No change for child light mode.

1. Wait until the paired resolver reports ready. Show **Copy address** and **Open Android network settings**, with a fallback to general Settings and instructions to search for **Private DNS** on OEM variants. Ask the user to select **Private DNS provider hostname**, paste and save. A light-mode app cannot enforce the global setting.
2. If moving from our VPN, record the chosen method and stop the tunnel as an intentional transition before checking Android DNS. Then let the user reconnect their VPN. On return, check with their VPN enabled and offer **Check filtering**. If setup fails, show one action to review the settings and an explicit path back to our VPN. Never take over the VPN slot without their choice or mark an intentional stop as revocation.
3. Use copy such as “Keep your VPN and use Plainphone for DNS when your VPN allows it. You can change this in Android Settings.” Show “Private DNS is set”, “Filtering verified on this connection”, “Plainphone DNS changed or is off”, or “Can't check filtering right now”. Include time of last successful check. Put compatible Tailscale instructions near the recovery action. Preserve accessible button labels, announcements, readable host wrapping and large-text layout in both languages and themes.

**Detection design.** Read `ConnectivityManager`'s default network for this app, then track `onLinkPropertiesChanged`, capabilities change, loss, foreground resume and existing status sync. Declare or reuse `ACCESS_NETWORK_STATE`. Compare `isPrivateDnsActive` and normalized `getPrivateDnsServerName` against the ready policy hostname, correlating callbacks to the current network. Automatic mode can be active with a null hostname. AOSP sets the active flag and host in strict mode even before any server validates. A match proves settings on that network, not reachability or whole-phone coverage. Underlying links are diagnostic only. When a VPN network hides the expected setting or the phone is offline, report unverified separately from a stable observed wrong hostname or off state. Never infer a user action from a lost or replaced network. [LinkProperties API][linkprops] · [AOSP DnsManager][dnsmanager]

For stronger evidence, use the ordinary Android resolver from the relevant network with a low-volume, first-party, cache-resistant canary pair. Give the blocked canary a deterministic Plainphone answer and an ordinary positive public answer, and use a separate allowed control. A timeout or both names failing is inconclusive. A successful direct DoT request would test the server and would say nothing about Android's effective resolver path. Report only outcome and time, without DNS history, VPN names or addresses. Scope the result to the tested app/network. Recheck after VPN or network changes. Keep the DNS method and health separate from Device Owner and lock integrity in status sync. Debounce transitions and reuse the protection notification deduplication pattern for a confirmed loss, preserving intentional method changes and an unknown state for older clients. Use existing retry and offline handling. [Current light tunnel](../../android/app/src/main/java/org/plainphone/app/light/vpn/PlainphoneVpnService.kt) · [Protection notifications](../../server/src/services/notifications.ts)

### DNS address in the dashboard

Under **Web filter**, show **Use this filter with your router or VPN** only after provisioning is ready. Copy the phone's DoT hostname and show port 853. Add a separately labelled **Copy DoH URL** once DoH is supported and advertised by the deployment. A small Tailscale guide should lead with Private DNS and opting the phone out of Tailscale DNS if MagicDNS is optional. For administrators who need MagicDNS, document the private forwarder option and which tailnet devices it can affect. A generic guide should ask for a DNS-over-TLS upstream field or an IT-managed forwarder. Show “Only devices and apps that send their DNS requests here use this filter. It blocks domains, and cannot filter pages inside a site, direct IP traffic, or apps using a different DNS service.” Sharing the address shares the phone's filter rules. Displaying or copying it conveys no protection status.

### One approved VPN in child strong mode

**Source-verified.** Clearing `DISALLOW_CONFIG_VPN` opens general user VPN configuration. It is too broad for approving one package. The documented owner-managed route is `setAlwaysOnVpnPackage(admin, packageName, lockdownEnabled)` while retaining the restriction. Android supports owner-configured always-on even with that restriction. API 31 and later clear a user-configured active VPN when the restriction is applied. AOSP's VPN preparation checks prevent another app taking over an always-on package. This API starts the specified VPN and persists it across reboot. It requires an installed compatible app. A package can opt out. The four-argument overload's list exempts packages from lockdown networking requirements. It grants no permission to run additional VPNs. [UserManager restriction][usermgr] · [Android Enterprise networking][dpc] · [DevicePolicyManager reference][dpm] · [AOSP VPN][aospvpn]

**Design.** Offer **Approve one VPN app** with the approved package's display name and an explanation visible to parent and child. Select from installed eligible packages and bind approval to package and signing identity. Apply and read back owner-managed always-on with lockdown **off** initially, retaining the VPN restriction and forced Private DNS. Label it as always-on because approval starts the app and Android attempts to reconnect it. The child may still need to sign in or complete an IT setup. Leave lockdown out of parent controls in the first release. Lockdown blocks connections when the tunnel is unavailable and can affect pairing, sync, captive portals and access to help. It does not force the VPN to use Plainphone DNS. If a company requires lockdown, treat it as a distinct compatibility decision after device testing.

Do not report success on receiving the desired policy. Report pending until the phone applies and reads it back. Handle unsupported apps, missing installs, signing changes, upgrade, offline changes and failed apply. Approve a replacement only after validating it. On revocation, clear the owner-configured VPN and verify that its tunnel is gone, VPN settings are still restricted and Plainphone DNS is restored and working. Test removal and recovery on API 29–30 separately. Preserve device-side recovery for a VPN that prevents policy sync, using the existing parent-authorized maintenance flow. Some child DNS rules may block the approved VPN's own control endpoints. Resolve compatibility with IT for the specific app and endpoints. Preserve child profile rules as the default.

**Activity and disclosure.** Read back the managed package separately from observing a VPN network. `TRANSPORT_VPN` describes a network and can miss apps with split routing. AOSP normally redacts the VPN owner UID from other apps. Use the managed-package readback plus VPN presence only after phone tests validate that correlation under the retained restriction. If attribution is uncertain, say “VPN detected” or “Connection unknown”. Send one parent event when a confirmed approved VPN becomes active, including the approved app name and time, with reconnect debouncing and idempotent delivery through existing sync/notifications. Show the same state on the child's phone. The tunnel being active says nothing about web filtering. [AOSP capability redaction][cs] · [Design principles](../design-principles.md)

Proposed parent confirmation and wording for the future update to [DNS bypass](../dns-bypass.md):

> When this VPN connects, it can send some or all DNS requests somewhere else. Plainphone's web filter may miss sites while the VPN is active. Phone rules such as app limits still apply. Plainphone tells you when it detects the approved VPN is connected.

Add to the threat model that approving the app trusts its tunnel, DNS policy, operator and any changeable configurations within it. An approved multi-provider VPN can still accept a different server profile inside the same app. Forced Android Private DNS remains configured. Test actual lookups before claiming coverage for that VPN. Keep approval explicit and reversible.

## Device verification before release

No Android emulator or physical-phone VPN tests ran in this job. Use an existing test phone and tailnet, a provisioned test resolver identity and synthetic names. Record model, OS build, resolver module and VPN version. Include a Pixel and Samsung or another supported OEM, an API 29–30 phone, and an API 31+ phone. Keep test output free of real hostnames, phone IDs and VPN credentials.

- On Wi-Fi and mobile, verify the baseline and the Tailscale rows above. Exercise on/off for **Use Tailscale DNS settings** independently of MagicDNS, override with and without the forwarder, then exit node off/on. For each, compare an allowed and blocked public lookup through Android's normal resolver, a MagicDNS lookup and a connection by tailnet IP. Check one included and one excluded app. Disable browser Secure DNS for the baseline and test it separately. Record the active network's VPN transport, Private DNS flags, observed canary result and a test-only resolver observation. An existing shell or debug build can use `adb shell dumpsys connectivity` and `adb shell dumpsys dnsresolver` locally to correlate net IDs, keeping raw dumps out of reports.
- Repeat with a company VPN or an administrator-provided test profile, full and split DNS, internal and public names, TCP 853 permitted and unavailable, and an unreachable provider. Exercise captive portal, reconnect, reboot and switching off or changing Private DNS. Verify recoveries and that unknown readings do not create protection-loss events.
- On a Device Owner phone, test approval before and after installing the VPN, unsupported app, authentication failure, restart, missing or changed package, second VPN rejection and revocation while connected. Confirm the child can see what the parent sees. Test lockdown only in a controlled device trial and verify help, policy sync and recovery. Test the case where Plainphone itself is excluded by the approved app's routing. Require honest unknown status anywhere presence or attribution cannot be observed.

## Proposed PR order

1. **Verify Android resolver observations.** Add the small Android observer and test canaries, run the phone matrix, document supported combinations and test the distinction between configured, verified, degraded and unknown. Keep observations local until the status contract is ready.
2. **Add protection status for alternate DNS.** Add an additive status contract and deduplicated transition handling. Test old/new payloads, retries, offline/unknown and intentional method changes. Publish health independently of lock or ownership.
3. **Offer Private DNS in Myself light mode.** Add onboarding, settings and recovery, and connect to the status from PR 2. Test switching both ways, DNS changed/off and VPN transitions. Evidence: Android's one-VPN rule and per-network Private DNS behavior. Direct evidence for well-being outcomes is unavailable.
4. **Show the DoT address for external DNS.** Add authenticated, readiness-gated copy and the Tailscale/router guides. Verify the forwarder profile on an existing test tailnet before labelling it supported. Evidence: Tailscale nameserver and AdGuard ClientID documentation.
5. **Expose DoH with per-profile ClientIDs.** Validate the proposed ID path and implement a TLS reverse proxy limited to the DoH route with GET/POST support and no management UI access. Prove allowed/blocked behavior for two profiles, reject unknown/missing IDs, omit identifiers from logs, verify per-profile caching isolation, certificate renewal and rollback. Advertise DoH via additive capability metadata, then enable its dashboard copy control. Evidence: AdGuard Home ClientID support and DoH-only clients. Arbitrary Tailscale console support is an independent upstream dependency.
6. **Prototype strong-mode owner-managed VPN on test devices.** Add the narrow policy adapter and test restriction retention, unsupported packages, loss of sync, rollback and the one-package invariant. Keep the parent control gated until approval and activity detection work on the target devices.
7. **Ship the strong-mode approval and notifications.** Add single-package approval/revocation to the parent surfaces, show matching child status, document the gap in `docs/dns-bypass.md` and update the policy reference. Test sync and notification deduplication, package changes and offline recovery. Evidence: Android Enterprise's owner-managed always-on API. No direct evidence that VPN approval improves safety outcomes. The purpose is access to a required VPN with the reduced filtering coverage made visible.
