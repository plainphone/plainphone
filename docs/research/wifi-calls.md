# Internet voice calls for Plainphone SOS, phase 2

**Research date:** 19 November 2026. **Decision:** Build authenticated one-to-one WebRTC with Plainphone-owned signalling and a dedicated EU coturn relay. Start with a child calling an enrolled parent. Add incoming calls on the child phone only after the child-side dialer and contact permissions pass physical-device tests. The feature works over a usable internet connection without a SIM or carrier coverage. Carrier calling and 112 stay on their independent Android telephony path.

**Confidence:** High means supported by a standard, platform document or inspected source. Medium means an engineering or legal inference from those sources. **UNVERIFIED** identifies untested integration behavior, unresolved legal applicability and estimates that require measurements or quotes.

## 1. Options and cost for 1,000 families

At 50 simultaneous calls, a single relay hop uses roughly 6.4 Mbit/s egress and the same ingress. These are sizing assumptions, with actual usage, relay ratio, concurrency and server capacity **UNVERIFIED**. Infrastructure budgets below are marginal monthly estimates before tax, staff time, store accounts, dedicated staging, redundancy and any commercial licences unless stated. ## 2. Receiving and ringing

### Android parent and child

- Use a high-priority **data** FCM message with a short TTL, opaque invitation identifier and no names, location, keys or SDP. Handle it in native code, including when the React Native runtime is cold. Validate expiry, deduplicate and produce a user-visible incoming call promptly. Firebase gives the handler only a few seconds and may downgrade high-priority messages that repeatedly produce no visible notification. A missing token, lack of Play services, force-stop, Doze/OEM policies or interrupted internet can prevent ringing. Treat FCM acceptance as a send result. [FCM priority](https://firebase.google.com/docs/cloud-messaging/android-message-priority) · [Receiving data messages](https://firebase.google.com/docs/cloud-messaging/android/receive-messages)
- Register a self-managed `PhoneAccount` and `ConnectionService` with `MANAGE_OWN_CALLS`, then use `addNewIncomingCall`. Respect Telecom rejection, busy and emergency-call arbitration. Own the notification and answer/decline actions. Use `CallStyle` on API 31+ and a compatible notification on API 29–30. Evaluate Jetpack Core-Telecom for the parent app, and test the classic service on the child where dialer visibility matters. Use native audio routing and start mic capture only after an explicit call action and applicable permissions/audio activation. Validate the target-SDK foreground-service rules and the exact self-managed `CallStyle` notification-permission exemption rather than assuming a blanket exemption. ### iOS parent

Register `PKPushRegistry` and `CXProvider` at native app launch. Send a dedicated APNs VoIP push to the PushKit token with the VoIP topic and short or zero expiration, separate from the ordinary Expo/FCM notification pipeline. Use a generic caller label and an opaque call UUID that can be reported even when protected app keys or JS are unavailable. In the legacy VoIP delegate, promptly report **every delivered VoIP push for a call to CallKit** before completing handling, without waiting on a fetch or JS. Failure can terminate the process and repeated failures can suppress launch. Complete verification and signalling in parallel. If the call has ended or fails verification, end the reported call promptly without enabling audio. Let CallKit activate the audio session and handle answer/decline/end natively across cold starts. [Apple PushKit handling](https://developer.apple.com/documentation/pushkit/responding-to-voip-notifications-from-pushkit) · [VoIP push type](https://developer.apple.com/documentation/PushKit/PKPushType/voIP)

Only create VoIP pushes for genuine new live calls. Deliver cancellation and state updates over signalling. Handle duplicate/stale deliveries against a stable UUID and confirm the exact report/error/completion sequence on devices. Newer Apple APIs expose a system-provided reporting requirement via VoIP push metadata. Use any no-report path only where the applicable API explicitly permits it. Version availability, duplicate behavior, termination versus user force-quit, pre-first-unlock behavior, Focus, and Expo cold-start integration remain **UNVERIFIED**. Ordinary SOS alerts use ordinary notifications. ## 5. Architecture and rollout

1. **Authenticate the call independently of the relay.** Extend [the encryption specification](../encryption.md) with a reviewed voice protocol after its encrypted feature prerequisite F3 and authenticated device admission are available on both platforms. Use the existing Ed25519 device identities, authenticated roster and per-recipient X25519 HPKE to sign and encrypt signalling. Domain-separate call messages. Bind call ID, caller, recipient, purpose, direction, roster state, expiry, revision and full offer/answer including DTLS fingerprints. Protect trickle ICE and renegotiation under the same context. Verify both peers against locally accepted grants and freshness, including revocation and reject stale or unverifiable state. A partitioned device may not know a newer revocation, a limitation inherited from the roster model. Avoid reusing H/R/L as media keys or treating a Find/Ring L grant as a calling grant. Let WebRTC negotiate ephemeral DTLS-SRTP media keys after endpoint checks. Exact protocol, native key access and implementation security are **UNVERIFIED** until reviewed and tested. [WebRTC trust and fingerprint model](https://www.rfc-editor.org/rfc/rfc8827.html)
2. **Keep the existing Hono/Postgres service as the control plane.** Authenticate transport and authorize routing against account/device state as defense in depth. Relay opaque envelopes over HTTPS, with a short-lived socket or fetch while ringing and active. Store transient invitations with explicit expiry and cleanup. Atomically resolve answer/cancel races across eligible parent devices and verify the winning device cryptographically at the caller. Bind the connection to that endpoint only. Show distinct local states for calling, answered, no answer and unavailable. Status should distinguish push sent, device acknowledged ringing, and verified two-way media. Keep durable call history out of the pilot. Application infrastructure sees routed IDs, timing and ciphertext sizes. APNs/FCM see token, timing and minimal call-wake metadata. Direct peers see network addresses. TURN sees endpoint transport IPs, allocations and traffic patterns, with audio encrypted. Exclude keys, payloads, tokens, SDP, peer IPs and child identifiers from routine logs. Keep aggregate reliability measures.
3. **Run coturn on a separate small EU VM for a family pilot.** Use a dedicated public endpoint with UDP for the preferred media path and TURN/TLS on TCP 443 for restrictive networks. Publish a bounded UDP relay range and enforce credentials, allocation limits, expiry and rate limits. Mint short-lived TURN credentials only for eligible endpoints. Deny internal and special-use relay destinations and monitor capacity and abuse. TCP 443 improves reachability but networks requiring HTTP proxies or application inspection may still block TURN. A shared web host is acceptable for a tightly scoped lab only if public IP/UDP allocation, firewall, TLS termination and service contention are checked. A separate relay avoids competition with the API's HTTPS listener and reduces resource contention and blast radius. Capacity and exact listener/firewall availability are **UNVERIFIED**. The existing control plane and single relay each remain a failure point. Pilot with aggregate probes and a reversible feature flag, then decide on a second relay based on observed failure and traffic. [coturn configuration and metrics](https://github.com/coturn/coturn) · [TURN RFC](https://www.rfc-editor.org/rfc/rfc8656.html)
4. **Phase 2a, child calls parent from SOS.** Use one explicit call action to an enrolled parent and ring that parent's approved devices. No inbound app-call UI on the child is needed in this phase. Provide clear unavailable and no-answer states. Keep existing SOS and separately implemented telephone options visible without silently switching transports. Use relay-only ICE for the initial pilot if hiding peer IPs from family contacts is a desired privacy guarantee. That choice needs both clients to suppress direct candidates and be checked through captured signalling. The baseline recommendation is direct ICE with self-hosted relay fallback and explicit disclosure of peer address visibility.
5. **Phase 2b, approved family calls.** Introduce explicit mutual call permissions and child-visible contacts/ring controls. Start with the same one-to-one media path. Add child-side ringing, inbound dialer integration where supported, per-contact safety controls, revocation handling and a local missed-call state. Block unknown callers, auto-answer and silent microphone activation. Keep app contact IDs separate from phone numbers and exercise conflicts with carrier calls, time limits and emergency callbacks. [Plainphone design principles](../design-principles.md)
