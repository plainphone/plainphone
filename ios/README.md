# iPhone native code

The Swift side of Plainphone on iPhone (phase 1, see [docs/ios/architecture.md](../docs/ios/architecture.md)).
The Plainphone app itself is the Expo app in [`parent-app/`](../parent-app). It links the Swift
code through the local Expo module [`parent-app/modules/plainphone-screentime`](../parent-app/modules/plainphone-screentime).
This folder builds and tests that Swift code on its own, with a project generated by
[xcodegen](https://github.com/yonaskolb/XcodeGen) from [`project.yml`](project.yml).

Nothing here is signed, and there is no team ID or secret in the repo.

## What is in the project

| Target | Sources | What it is |
|---|---|---|
| `PlainphoneCore` (framework) | `parent-app/modules/plainphone-screentime/ios/Core` | Rules document, compiler, stores, App Group plan, receipt, the `ScreenTimeApplying` seam with `FamilyControlsApplier` and `FakeScreenTime` |
| `PlainphoneCoreTests` | `Tests/PlainphoneCoreTests` | Unit tests; `Tests/Fixtures/ios-rules.json` is a real server document |
| `ActivityMonitor`, `ShieldConfiguration`, `ShieldAction` (app extensions) | `parent-app/modules/plainphone-screentime/targets/*` | The Device Activity Monitor and the two shield extensions |
| `PlainphoneDev` (app) | `Host` | A small SwiftUI host that embeds the extensions, for simulator builds and for running the spikes on a test iPhone. Not the Plainphone app |

The fixture is checked against the server by `server/test/ios-contract.test.ts`. After a deliberate
change to the iPhone rules document, regenerate it with
`cd server && UPDATE_IOS_FIXTURE=1 pnpm vitest run test/ios-contract.test.ts`.

## Build and test on a Mac

Needs Xcode 26 and xcodegen 2.46 (`brew install xcodegen`, or the release zip CI uses).

```sh
ios/scripts/ci.sh        # generate, build for the simulator, run the unit tests (unsigned)
```

To open it in Xcode: `cd ios && xcodegen generate && open PlainphoneDev.xcodeproj`. For a test
iPhone, pick your team under Signing & Capabilities; the dev host uses bundle IDs under
`org.plainphone.app.dev` (`PP_BUNDLE_ID` in `project.yml`), so it never collides with the App
Store app. Use a test family, never a real child's Apple Account.

## Check the logic without a Mac

```sh
ios/scripts/linux-check.sh    # needs Docker; official swift:6.2 image
```

It builds `PlainphoneCore` and runs its tests on Linux, in Swift 5 mode (as the Expo pod builds it)
and in Swift 6 mode with warnings as errors. The Apple-only parts (`FamilyControlsApplier`, the
extensions, the dev host) are left out there; the `ios` CI job on macOS builds them.

## CI

The `ios` job in [`.github/workflows/ci.yml`](../.github/workflows/ci.yml) runs on `macos-latest`
when `ios/` or the Swift module changes (otherwise it reports "up to date" on Linux). It picks the
newest Xcode 26, installs the pinned xcodegen release with a checksum, and runs `ios/scripts/ci.sh`.

## Seams that wait for a real iPhone

Every part that depends on a spike in [docs/ios/spikes.md](../docs/ios/spikes.md) is behind the
`ScreenTimeApplying` protocol or marked `TODO(spike …)`:

| Spike | Where | Until then |
|---|---|---|
| (a) token round trip | `FamilyControlsApplier.apply`, `pickActivities` in the Expo module | There is no app picker yet (`pickActivities` throws), so the selection is always empty: in closed mode (allow list) every app except Apple's built-in ones is shielded and none can be opened; open mode shields nothing. An unreadable selection shields every app (allow list) or keeps the shield in place (open mode) |
| (b) shield action | `ShieldActionExtension`, `ShieldConfigurationExtension` | The shield has one button that closes the app; "Ask for more time" only records an App Group event |
| (d) push latency | `ActivityMonitorExtension`, `parent-app/src/app/child/index.tsx` | Rules sync while the app is open and when it comes to the front |
| (e) Declared Age Range | the Apple-settings step of the wizard | The wizard guides; it says it cannot check the settings |

School time, bedtime and the daily limit wait for phase 2 behind one switch,
`IosEnforcement.enforcesSchedules` (`false`): they are compiled into the plan but not monitored and
not reported as failed ([architecture](../docs/ios/architecture.md#phase-1-what-the-iphone-does-not-enforce-yet)).
